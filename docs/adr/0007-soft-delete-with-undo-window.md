# 删除改成打记号，配撤销窗口，回收站不设

「买摄像头」误删事件暴露的坑：删除是硬删+墓碑，救回来纯粹靠 Mac 端恰好没同步到——两端同步过之后，原文就只在云端历史里，实际等于没了。本决定把删除从「抹掉」改成「打记号」：**删除给记录打上删除时刻（`deletedAt`），从一切界面消失，数据永远留着，不清理；唯一的反悔路是删除后的撤销窗口，回收站不设。** 待办、分类、收藏三种删除同一套待遇——「删待办能反悔、删收藏不能」是一条要人记住的规矩，与 ADR-0003 同一条理由推翻。

撤销窗口的口径：**占位跟着死者的原位走**——待办在它那一行的位置浮出「已删除 · 撤销」的占位（一条待办活在几处，占位就在几处），分类在 tab 栏原位留占位胶囊，收藏在流里原位占位行，三种删除同一句话。每次删除各有一个占位、各自倒计时、各自撤——连删几条也救得准中间那条；⌘Z 按删除时间从新到旧收，不管占位在不在眼前，与占位同一个寿命。只在删除发生的这台设备、这次会话里有效；远端来的删除不弹占位，静静落下。

存储不动：`deletedAt` 是模型层的一个可空字段，JSON 照存。时间戳三要素是字段约定，不是存储引擎的功能；为它换数据库（MySQL/SQLite）被拒绝——MySQL 在 iOS 上根本跑不起来，与 ADR-0006 的共享核心正面冲突，SQLite 则该由真实的痛（载入慢、复杂查询）驱动，不搭这次的便车。

## Considered Options

- **撤销窗口盖在硬删上（窗口一过真删）** —— 拒绝：`deletedAt` 沦为撤销的实现细节，「事后好几天才发现」的误删依然没救，可那正是这次事件的形状。
- **软删除 + 回收站** —— 暂缓：恢复能力最强，但回收站是一个全新的常驻界面，眼下不要；数据反正永远留着，哪天要做只是加个界面的事，退路已留足。
- **只提高删除门槛（确认弹窗 / 加大距离）** —— 拒绝：治标，长按菜单里照样误点，真误删了还是没救。
- **撤销窗口住底部浮条 / tab 栏右端** —— 形态三案 mock 对比后取原位占位：反悔发生在案发现场，「占位跟着死者的原位走」一条规矩盖住三种删除；代价是占位塌缩时布局动一下，接受。浮条被拒是不想给 app 养第一个浮在内容上的构件；tab 栏右端被拒是离手最远，且与「无视中断」那句非控件的话贴脸。
- **删除态记录过期清理（如 30 天）** —— 拒绝：待办是几行文字，清理省下的空间约等于零，却要回答谁来清、清理走哪条同步路、清一半断网怎么办；墓碑机制因此退不了役。

## Consequences

- **「删除胜」退役。** 删除记号只是记录的一个方面，套普通的字段级合并：这台删、那台改字，两边都保住——撤销救回来的正是改过的字；这台删、那台撤销，后写的算。同步的特判表少一行，「一次只动一样」不再有例外。
- **同步墓碑整体退役。** 删除在同步里是一次普通的 `recordSave`，CloudKit 记录从此只增改、不消失；`SyncChangeLog` 里的墓碑、殉葬品那套机制没有存在理由了（迁移期怎么退场是实现的事）。
- **「非空分类删不掉」留任，理由换了**：撤销窗口救得回一条手滑，救不回一批——整个分类几十条待办一起进删除态，几秒钟里看不清丢了什么，宁可事前拦。「非空」数的是活着的待办：全躺在删除态里的分类算空，照删。
- **一条不变式贯穿撤销与同步：活着的待办，它的分类必须活着。** 哪条路救活一条待办，分类就跟着复活；「待办胜、分类复活」是它在同步冲突里的样子。
- CONTEXT.md 里「删除没有撤销、没有回收站」的两处论证已随本决定改写；「删除在这里本就是郑重的表态」这句话作废——郑重的是「彻底抹掉」，而这里从此没有这个动作。
