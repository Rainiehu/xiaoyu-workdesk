# 多设备同步走 iCloud（CloudKit），Azure 退场

目的是让同一份待办出现在这台 Mac 和将来的 iPhone 上 —— 是**同步**，不是备份。手上虽有 Azure 账号和额度，仍决定走 CloudKit（CKSyncEngine）：额度是资源不是需求，而逐条记录的推拉、离线暂存、冲突回调这一整套，CloudKit 是现成引擎，Azure 路线上得从头手写 —— 自制版还没有它可靠。本地文件仍是界面的唯一事实来源，断网时 app 就是一台完整的单机 app，引擎只在底下逐条记录推拉。

## Considered Options

- **Azure（对象存储/数据库 + 自建 API）** —— 拒绝：平台中立的优势只在「网页端 / 非 Apple 设备」兑现，而那对一个个人案头工具大概率是虚构需求；代价却是常驻的 —— 同步协议、离线合并、冲突处理全部自养。
- **iCloud Drive 文件夹（免 entitlement，直接把存储目录挪过去）** —— 拒绝：同步单位是整个文件，两台设备同时开着 app 各改各的，后写的整份数据把先写的覆盖掉 —— 按「每次改动全量落盘」的写法，这是真实的丢数据风险；绕开它要自制按设备分文件再合并的逻辑，那正是 CloudKit 已经替你写好的部分。

## Consequences

- 付费开发者账号成为依赖（做 iPhone 版横竖躲不掉）；SPM 直接构建的裸 bundle 要补齐签名与 provisioning。
- 锁进 Apple 生态：网页端 / 非 Apple 设备这扇门关上 —— 明确接受，不为它留门。
- 同步的范围与冲突规矩是领域语言，定在 CONTEXT.md 的 Notes 里（字段级合并、删除胜、分类复活、顺序照旧）；ADR-0002 的紧凑整数排序不动。
